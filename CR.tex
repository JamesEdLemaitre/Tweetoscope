\section{Secrets et Git}

Lors du développement d'applications impliquant l'accès à un service distant via une clé API privée ou des identifiants, il est crucial de ne pas les divulguer dans un dépôt public par exemple.

Cela peut être particulièrement délicat car même la suppression des identifiants dans les versions ultérieures du code n'empêchera pas d'autres personnes de consulter les anciens commits et de lire ces jetons.

Les pirates informatiques peuvent utiliser ces jetons pour différentes raisons, notamment accéder à une API privée qui ne leur est pas accessible (certains accès API peuvent être liés à un compte et ainsi accéder à des données privées. Cela peut être le cas par exemple avec l'API Spotify qui permet d'accéder à vos données privées via votre clé API), voler des crédits payants, abuser de l'accès jusqu'à ce que la clé soit bannie pour trop de requêtes par exemple.

Au lieu d'écrire les jetons à l'intérieur du code comme une variable, il est préférable de les écrire dans un fichier \texttt{config.properties} et d'ajouter ce fichier au \texttt{.gitignore}.

Pour les projets professionnels, des outils spécialisés comme Azure Key Vault peuvent être utilisés.

D'autres outils peuvent permettre aux développeurs de scanner les modifications avant de commiter automatiquement, ou de scanner un dépôt pour vérifier si des secrets sont inclus dans le code.

\subsection{Choix du nombre de partitions}

Le dimensionnement des partitions pour chaque topic est justifié par les conditions réelles d'exploitation et les volumes de données attendus :

\subsubsection{Topic \texttt{raw-tweets} : 1 partition}

\textbf{Justification :} Dans un contexte de production réel avec un volume important de tweets (millions par jour), ce topic nécessiterait plusieurs partitions pour paralléliser l'ingestion. Cependant, pour ce TP avec un dataset limité et un besoin de préserver l'ordre chronologique des tweets lors de leur lecture, une seule partition suffit et simplifie l'implémentation.

\subsubsection{Topic \texttt{filtered-tweets} : 1 partition}

\textbf{Justification :} Le filtrage réduit considérablement le volume de données. Même en production avec de gros volumes initiaux, le débit après filtrage restrait gérable par une seule partition pour un grand nombre de données(ou en tout cas, beaucoup moins qu'inititalement). 

\subsubsection{Topic \texttt{hashtags} : 3 partitions}

\textbf{Justification :} C'est le topic critique nécessitant du partitionnement :
\begin{itemize}
    \item \textbf{Volume élevé :} Chaque tweet peut contenir plusieurs hashtags, multipliant le nombre de messages
    \item \textbf{Cohérence du comptage :} Le partitionnement par clé (hashtag) garantit que tous les messages concernant un même hashtag arrivent à la même partition, permettant un comptage cohérent
    \item \textbf{Parallélisation :} 3 partitions permettent de distribuer la charge sur 3 instances de \texttt{KafkaHashtagCounter} via un consumer group
\end{itemize}

Le nombre de 3 est indicatif comme les autres, basé sur le fait qu'on s'attend à avoir environ 3 hashtags par tweet en moyenne. Pour le TP, une seule partitiuon suffit. 

\subsubsection{Topic \texttt{leaderboard} : 1 partition}

\textbf{Justification :} Ce topic contient uniquement les agrégations finales (top N hashtags), donc un très faible volume de messages. Une seule partition suffit et permet de préserver l'ordre temporel des mises à jour du classement pour l'affichage.

\subsection{Stratégie de partitionnement}

\section{Analyse des risques / Analyse initiale des risques}

\underline{Impact d'une défaillance du Tweet Producer} :

Les nouveaux tweets ne sont plus reçus par l'application.

Il n'y aura pas de crash, et la restauration de cet élément permettra à l'application de fonctionner à nouveau normalement.

\underline{Impact d'une défaillance du Tweet Filter} :

Les tweets bruts ne sont pas filtrés et transmis aux composants suivants. Les messages s'accumuleront dans le topic \texttt{raw-tweets}. La restauration de cet élément entraînera le filtrage de tous les tweets bruts sans aucune perte d'information.

\underline{Impact d'une défaillance du Hashtag Extractor} :

Les hashtags ne sont plus extraits des tweets. Les tweets filtrés s'accumuleront dans le topic \texttt{filtered-tweets}. La restauration de cet élément entraînera l'extraction des hashtags des tweets filtrés sans aucune perte d'information.

\underline{Impact d'une défaillance du Hashtag Counter} :

Les hashtags ne sont plus comptabilisés. Sans mesure supplémentaire, la restauration de cet élément peut entraîner des erreurs dans les résultats : la mémoire du nombre d'apparitions passées de chaque hashtag sera perdue et réinitialisée à $0$.

\underline{Impact d'une défaillance du Visualizor} :

Il n'est plus possible de voir les résultats. La restauration de cet élément permettra d'afficher à nouveau les résultats, sans aucune erreur dans les données affichées.

\underline{Impact d'une défaillance d'un Broker} :

La défaillance d'un broker ne sera pas un problème s'il est répliqué.



\section{Task 9}

\subsection{Compilation}

Tous les composants Kafka ont été implémentés en Java et compilés avec Maven. La compilation s'effectue avec la commande suivante :

mvn -f ./pom.xml clean package

Note importante : La structure du pom.xml a dû être modifiée pour être correcte pour éviter des erreurs de compilation et des dépendances manquantes. C'est cette commande qui crée tous les .jar qui seront exécutés dans le terminal pour lancer les services Kafka. 

Les fichiers .jar sont créés sous :

target/<Nom du service>-jar-with-dependencies.jar

Par exemple, pour le producer des raw-tweets:

java -jar target/KafkaTweetProducer-jar-with-dependencies.jar

\subsection{Serveur Kafka}

Avant de lancer les composants, le serveur Kafka doit être démarré :

\textbf{Génération d'un UUID pour le cluster :}

\begin{verbatim}
KAFKA_CLUSTER_ID="$($KAFKA_HOME/bin/kafka-storage.sh random-uuid)"
\end{verbatim}

\textbf{Formatage du storage :}

\begin{verbatim}
$KAFKA_HOME/bin/kafka-storage.sh format --standalone -t $KAFKA_CLUSTER_ID \
  -c $KAFKA_HOME/config/server.properties
\end{verbatim}

\textbf{Démarrage du serveur Kafka :}

\begin{verbatim}
$KAFKA_HOME/bin/kafka-server-start.sh $KAFKA_HOME/config/server.properties
\end{verbatim}

\subsection{Création des topics}

Les topics nécessaires doivent être créés avant le lancement des composants :

\textbf{Topic pour les tweets bruts :}

\begin{verbatim}
$KAFKA_HOME/bin/kafka-topics.sh --create --bootstrap-server localhost:9092 \
  --replication-factor 1 --partitions 1 --topic raw-tweets
\end{verbatim}

\textbf{Topic pour les tweets filtrés :}

\begin{verbatim}
$KAFKA_HOME/bin/kafka-topics.sh --create --bootstrap-server localhost:9092 \
  --replication-factor 1 --partitions 1 --topic filtered-tweets
\end{verbatim}

\textbf{Topic pour les hashtags extraits :}

\begin{verbatim}
$KAFKA_HOME/bin/kafka-topics.sh --create --bootstrap-server localhost:9092 \
  --replication-factor 1 --partitions 1 --topic hashtags
\end{verbatim}

\textbf{Topic pour le leaderboard :}

\begin{verbatim}
$KAFKA_HOME/bin/kafka-topics.sh --create --bootstrap-server localhost:9092 \
  --replication-factor 1 --partitions 1 --topic leaderboard
\end{verbatim}


\subsection{Lancement des composants}

\textbf{KafkaTweetProducer}

Commande:

java -jar target/KafkaTweetProducer-jar-with-dependencies.jar [random|recorded]

Options:

\begin{enumerate}
\item random: implémente le producer random présent dans la version initiale du projet. 

\item recorded: implémente le producer lisant un fichier contenant des tweets au format .json.

Pour l'utiliser, il faut bien penser à créer une variable d'environnement précisant où se trouve le fichier source:

export tweetoscope\_sourcefile="..."

Contrairement au random, il ne fonctionne pas indéfiniment. Il ne lit qu'une seule fois le contenu du fichier puis s'arrête. 
 
\end{enumerate}

\textbf{KafkaTweetFilter}

Ce composant consomme les tweets du topic raw-tweets, les filtre et publie les tweets filtrés dans filtered-tweets :

java -jar target/KafkaTweetFilter-jar-with-dependencies.jar [option] [paramètre]

Note d'implémentation : La classe RecentTweetFilter a été réimplémentée sans utiliser le pattern .subscribe(). Cette approche diffère du code initial mais respecte le modèle consumer-producer de Kafka.

Options:

\begin{enumerate}
\item recent 

Comportement : Ne conserve que les tweets créés il y a moins de 24 heures.

Critère : Compare la date de création du tweet (createdAt) avec l'heure actuelle.

\item lang [codelangue] 

Comportement : Ne conserve que les tweets dans la langue spécifiée. Si aucun code de langue n'est fourni, "en" (anglais) est utilisé par défaut.

Critère : Compare le champ lang du tweet avec le code langue fourni.

\item empty

Comportement : Ne filtre que les tweets ayant un contenu textuel non vide (après suppression des espaces).

\end{enumerate}

\textbf{KafkaHashtagExtractor}

Ce composant consomme les tweets filtrés et extrait les hashtags :

java -jar target/KafkaHashtagsExtractor-jar-with-dependencies.jar

\textbf{KafkaHashtagCounter}

Ce composant compte les occurrences de chaque hashtag et publie les résultats dans le topic leaderboard :
java -jar target/KafkaHashtagCounter-jar-with-dependencies.jar

\textbf{Leaderboard}

Ce composant consomme le topic leaderboard et affiche les résultats :

java -jar target/KafkaLeaderboard-jar-with-dependencies.jar

\section{Vérification expérimentale de l'analyse des risques}

\subsection{Défaillance du Tweet Producer}

Gravité: Moyenne à forte

$\rightarrow$ Le leaderboard reste affiché avec des informations qui deviennent de plus en plus fausses pendant la durée de la panne. Le problème est que remettre le producer en route (en supposant qu'on est Online, connectés à l'API) ne nous permet pas de récupérer les Tweets publiés entre temps. Les informations affichées seront donc faussées durant une certaine période, qui peut dépendre par exemple du temps mis dans le filtre "recent" s'il est utilisé. 

Détectabilité: Moyenne ou forte

$\rightarrow$ Il n'y a pas de message d'erreur, mais on remarquera assez facilement que le leaderboard ne se met plus à jour

\subsection{Défaillance du Tweet Filter}

Gravité: Faible

$\rightarrow$ Les tweets bruts s'accumulent dans le topic \texttt{raw-tweets} sans être traités. Le reste de la chaîne continue de fonctionner normalement avec les derniers tweets filtrés. Aucun composant ne crashe. Lorsque le filtre est relancé, il reprend le traitement de tous les tweets accumulés grâce au mécanisme de consumer groups de Kafka, sans perte de données.

Détectabilité: Moyenne

$\rightarrow$ Aucun message d'erreur visible. On peut détecter la panne en vérifiant le lag du consumer group qui augmente progressivement, ou en constatant que de nouveaux tweets ne sont plus filtrés alors que le producer continue de publier.

\subsection{Défaillance du Hashtag Extractor}

Gravité: Faible

$\rightarrow$ Les tweets filtrés s'accumulent dans le topic \texttt{filtered-tweets} sans que les hashtags soient extraits. Le comportement est similaire à la défaillance du filtre : le système reste stable, les messages s'accumulent, et la reprise du service permet de traiter l'intégralité des tweets en attente sans perte de données.

Détectabilité: Moyenne

$\rightarrow$ Pas de message d'erreur. La détection se fait par l'observation du lag du consumer group correspondant, ou par l'absence de mise à jour du leaderboard alors que de nouveaux tweets filtrés arrivent.

\subsection{Défaillance du Hashtag Counter}

Gravité: Forte

$\rightarrow$ Les hashtags extraits s'accumulent dans le topic \texttt{hashtags} mais ne sont plus comptabilisés. Le problème majeur confirmé expérimentalement est la \textbf{perte de l'état en mémoire} : lorsque le counter est relancé, les compteurs repartent à zéro. Les hashtags reçus pendant la panne sont bien traités à la reprise, mais l'historique des comptages précédents est perdu, ce qui fausse complètement les résultats du leaderboard.

Détectabilité: Forte

$\rightarrow$ La détection est immédiate après redémarrage : on observe que les compteurs ont été réinitialisés (ex: un hashtag qui était à 50 apparitions repasse à 0 ou à un petit nombre). Cette anomalie dans les valeurs affichées permet de détecter rapidement qu'il y a eu une défaillance.

\subsection{Défaillance du Visualiseur}

Gravité: Très faible

$\rightarrow$ L'affichage du leaderboard n'est plus disponible, mais toute la chaîne de traitement continue de fonctionner normalement. Les résultats continuent d'être produits et publiés dans le topic \texttt{leaderboard}. Lorsque le visualiseur est relancé, il affiche immédiatement les dernières données disponibles sans aucune perte d'information.

Détectabilité: Immédiate

$\rightarrow$ L'absence d'affichage est immédiatement visible pour l'utilisateur. Cependant, on peut vérifier que les données continuent d'être produites en consultant directement le topic \texttt{leaderboard} avec un consumer console.

\subsection{Défaillance d'un Broker}

Gravité: Critique (sans réplication) / Faible (avec réplication)

$\rightarrow$ Dans notre configuration actuelle avec un seul broker (\texttt{replication-factor=1}), la défaillance du broker entraîne l'arrêt complet de l'application : tous les topics deviennent inaccessibles et tous les composants sont bloqués. Avec une configuration répliquée sur plusieurs brokers, la défaillance d'un broker n'affecterait pas le fonctionnement global grâce à la redistribution automatique des partitions sur les brokers restants.

Détectabilité: Immédiate

$\rightarrow$ Tous les composants génèrent des erreurs de connexion et l'application s'arrête complètement. La détection est donc immédiate.

\section{Task 11 : Conteneurisation Docker}

\subsection{Principes de la Conteneurisation}

Docker permet d'empaqueter l'application avec toutes ses dépendances (JRE, librairies, configurations) dans un conteneur léger et portable. Cela garantit que l'application fonctionne de manière identique sur tout environnement : machine de développement, serveur de test, ou cluster de production.

Notre projet utilise une image Docker unique \texttt{fthievon/tweetoscope-kafka:latest} pour tous les microservices (Producer, Filter, Extractor, Counter, Leaderboard). Cette approche est possible car tous les services partagent le même code de base et seul le JAR exécuté change selon le service déployé.

\subsubsection{Travaux Effectués}

\begin{itemize}
    \item \textbf{Création du Dockerfile} : Implémentation d'une stratégie multi-stage avec deux étapes distinctes
    \begin{itemize}
        \item Stage 1 (build) : Compilation du projet Maven avec \texttt{maven:3.9-eclipse-temurin-11}
        \item Stage 2 (runtime) : Image légère \texttt{eclipse-temurin:11-jre-alpine} contenant uniquement la JRE
    \end{itemize}
    \item \textbf{Configuration des variables d'environnement} : Mise en place du système pour passer \texttt{SERVICE\_JAR}, \texttt{KAFKA\_BOOTSTRAP\_SERVERS} et \texttt{ARGS}
    \item \textbf{Build et Push sur DockerHub} : Construction locale et publication de l'image sur le registre public
    \item \textbf{Exposition du port 8080} : Configuration pour le leaderboard web server
    \item \textbf{Optimisation de la taille} : Réduction significative par l'utilisation d'une image alpine pour le runtime
\end{itemize}

\subsection{Fichier Dockerfile et Architecture Multi-Stage}

Le Dockerfile suit une approche multi-stage pour réduire la taille de l'image finale :

\begin{enumerate}
    \item \textbf{Stage de compilation} : Utilise \texttt{maven:3.9-eclipse-temurin-11} pour compiler le projet Maven et générer les JARs
    \item \textbf{Stage d'exécution} : Utilise \texttt{eclipse-temurin:11-jre-alpine} (image légère avec uniquement la JRE) pour exécuter l'application
\end{enumerate}

Le conteneur expose le port 8080 (utilisé par le leaderboard web server) et accepte des variables d'environnement pour configurer le service à lancer :

\begin{itemize}
    \item \texttt{SERVICE\_JAR} : Le JAR à exécuter (ex: \texttt{KafkaTweetFilter})
    \item \texttt{KAFKA\_BOOTSTRAP\_SERVERS} : Adresse du broker Kafka (ex: \texttt{kafka:9092})
    \item \texttt{ARGS} : Arguments supplémentaires passés au service
\end{itemize}

\subsection{Utilisation et Déploiement}

\subsubsection{Construction locale}

Pour construire l'image Docker localement :

\begin{verbatim}
docker build -t tweetoscope-kafka .
\end{verbatim}

\subsubsection{Exécution d'un service}

Pour lancer un service spécifique en local :

\begin{verbatim}

  -e KAFKA_BOOTSTRAP_SERVERS=localhost:9092 \
  tweetoscope-kafka
\end{verbatim}

\subsubsection{Publication sur le registre}

Pour déployer en production sur le registre DockerHub :

\begin{verbatim}
docker push fthievon/tweetoscope-kafka:latest
\end{verbatim}

\subsection{Avantages de la Conteneurisation}

$\rightarrow$ \textbf{Portabilité} : L'image fonctionne sur tout environnement ayant Docker

$\rightarrow$ \textbf{Isolation} : Chaque conteneur a son propre système de fichiers et ses ressources

$\rightarrow$ \textbf{Scalabilité} : On peut rapidement créer plusieurs instances d'un même service

$\rightarrow$ \textbf{Reproductibilité} : Les mêmes versions des dépendances sont utilisées partout

\section{Task 12 : Orchestration Kubernetes}

\subsection{Introduction à Kubernetes}

Kubernetes (K8s) est un orchestrateur de conteneurs qui automatise le déploiement, la mise à l'échelle et la gestion des applications conteneurisées. Contrairement à Docker Compose qui fonctionne sur une seule machine, Kubernetes gère des clusters avec plusieurs nœuds physiques et distribue les conteneurs de manière optimale.

Dans notre projet, nous utilisons Kubernetes pour orchestrer les 5 microservices de Tweetoscope et Apache Kafka sur un cluster, assurant ainsi une disponibilité élevée et une résilience aux défaillances.

\subsubsection{Travaux Effectués}

\begin{itemize}
    \item \textbf{Configuration du cluster Kubernetes} : Mise en place d'un cluster Kind (Kubernetes in Docker) pour développement et tests locaux
    \item \textbf{Création de 5 fichiers de déploiement YAML} : Un pour chaque microservice (Producer, Filter, Extractor, Counter, Leaderboard)
    \item \textbf{Configuration des services réseau} : Exposition du leaderboard web server sur le port 8080
    \item \textbf{Gestion des variables d'environnement} : Passage des configurations Kafka aux conteneurs via deployments YAML
    \item \textbf{Intégration des images Docker} : Utilisation de \texttt{fthievon/tweetoscope-kafka:latest} depuis DockerHub (images publiques)
    \item \textbf{Suppression de imagePullSecrets} : Simplification en utilisant des images publiques (pas d'authentification nécessaire)
\end{itemize}

\subsection{Structure du Cluster et des Deployments}

Un cluster Kubernetes se compose de :

\begin{itemize}
    \item \textbf{Nœuds (Nodes)} : Machines physiques ou virtuelles qui exécutent les conteneurs
    \item \textbf{Pods} : Unité minimale de déploiement contenant un ou plusieurs conteneurs
    \item \textbf{Deployments} : Spécifications pour maintenir un nombre donné de replicas d'un Pod
    \item \textbf{Services} : Points d'accès réseau pour communiquer avec les Pods
\end{itemize}

Notre projet contient 5 fichiers de déploiement dans le répertoire \texttt{k8s/} :

\begin{enumerate}
    \item \texttt{tweetoscope-producer-deployment.yaml} : Produit les tweets
    \item \texttt{tweetoscope-filter-deployment.yaml} : Filtre les tweets
    \item \texttt{tweetoscope-extractor-deployment.yaml} : Extrait les hashtags
    \item \texttt{tweetoscope-counter-deployment.yaml} : Compte les occurrences
    \item \texttt{tweetoscope-leaderboard-deployment.yaml} : Affiche le leaderboard (avec service web)
\end{enumerate}

Chaque deployment utilise l'image Docker \texttt{fthievon/tweetoscope-kafka:latest} du registre public DockerHub. Puisque l'image est publique, aucune authentification (imagePullSecrets) n'est nécessaire.

\subsection{Deployments et Services}

Chaque deployment Kubernetes spécifie :

\begin{itemize}
    \item \textbf{Nombre de replicas} : Combien de copies du Pod doivent tourner simultanément
    \item \textbf{Conteneur} : Image Docker, variables d'environnement, limites de ressources
    \item \textbf{Sélecteurs} : Identifiants pour trouver et gérer les Pods
\end{itemize}

Le service \texttt{tweetoscope-leaderboard-service.yaml} expose le web server du leaderboard sur le port 8080, le rendant accessible depuis l'extérieur du cluster. Les autres services communiquent via les noms DNS internes Kubernetes (ex: \texttt{kafka:9092} est automatiquement résolu vers le broker Kafka).

\subsection{Variables d'Environnement et Configuration}

Chaque deployment passe des variables d'environnement au conteneur :

\begin{itemize}
    \item \texttt{SERVICE\_JAR} : Défini selon le service (KafkaTweetFilter, KafkaHashtagCounter, etc.)
    \item \texttt{KAFKA\_BOOTSTRAP\_SERVERS} : Pointe vers le service Kafka interne du cluster
    \item \texttt{ARGS} : Arguments supplémentaires pour le filtrage, la langue, etc.
\end{itemize}

\subsection{Déploiement sur Kubernetes}

Pour déployer tous les services sur le cluster :

\begin{verbatim}

\end{verbatim}

Pour vérifier le statut des deployments :

\begin{verbatim}
kubectl get deployments
kubectl get pods
kubectl logs <pod-name>
\end{verbatim}

Pour redimensionner un service (ex: 3 replicas du filter) :

\begin{verbatim}

  --replicas=3
\end{verbatim}

\subsection{Avantages de Kubernetes vs Docker Compose}

$\rightarrow$ \textbf{Haute disponibilité} : Si un Pod crashe, un nouveau remplace automatiquement

$\rightarrow$ \textbf{Scalabilité horizontale} : Ajouter des replicas se fait en une commande

$\rightarrow$ \textbf{Gestion des nœuds} : Distribue les Pods optimalement sur les nœuds disponibles

$\rightarrow$ \textbf{Rolling updates} : Mises à jour sans interruption du service

$\rightarrow$ \textbf{Isolation réseau} : Services communiquent via DNS sans exposition inutile

$\rightarrow$ \textbf{Production-ready} : Standard de l'industrie pour les applications distribuées

\subsection{Défis et Limitations}

$\rightarrow$ Kubernetes est plus complexe que Docker Compose et nécessite une courbe d'apprentissage

$\rightarrow$ La configuration réseau et les troubleshooting peuvent être complexes

$\rightarrow$ Pour un petit projet, Docker Compose peut être suffisant et plus simple à mettre en place

$\rightarrow$ Dans notre cas, nous avons utilisé Kind (Kubernetes in Docker) pour développer et tester localement avant le déploiement en production

\section{Task 14 : Tests JUnit pour KafkaTweetFilter}

\subsection{Objectif}

\subsection{Structure des Tests}

La classe de test \texttt{KafkaTweetFilterTest.java} contient 7 tests couvrant les scénarios principaux :

\subsubsection{Test 1: testEmptyTweetFilterAcceptsAllTweets}

Valide que le filtre "empty" accepte tous les tweets reçus sans en rejeter aucun. C'est un filtre pass-through qui ne modifie pas les données.

\subsubsection{Test 2: testLangTweetFilterAcceptsEnglish}

Vérifie que le filtre "language" accepte les tweets dont le champ \texttt{lang} est défini à \texttt{"en"} (anglais).

\subsubsection{Test 3: testLangTweetFilterRejectsFrench}

Valide que le filtre "language" rejette les tweets en français (\texttt{lang = "fr"}).

\subsubsection{Test 4: testRecentTweetFilterAcceptsRecentTweets}

Teste que le filtre "recent" accepte les tweets créés depuis moins de 24 heures (en comparant le timestamp avec l'heure actuelle).

\subsubsection{Test 5: testRecentTweetFilterRejectsOldTweets}

Valide que le filtre "recent" rejette les tweets créés depuis plus de 24 heures.

\subsubsection{Test 6: testGsonSerializationDeserialization}

Vérifie que la sérialisation/désérialisation JSON avec Gson fonctionne correctement pour les tweets (l'objet Tweet peut être converti en JSON et reconverti sans perte de données).

\subsubsection{Test 7: testNullTweetHandling}

Teste le traitement des cas limites : que se passe-t-il quand on essaie de déserialiser une chaîne JSON vide ou invalide. Le test vérifie que le résultat est \texttt{null}.
