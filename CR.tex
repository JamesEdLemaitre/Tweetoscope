\section{Secrets et Git}

Lors du développement d'applications impliquant l'accès à un service distant via une clé API privée ou des identifiants, il est crucial de ne pas les divulguer dans un dépôt public par exemple.

Cela peut être particulièrement délicat car même la suppression des identifiants dans les versions ultérieures du code n'empêchera pas d'autres personnes de consulter les anciens commits et de lire ces jetons.

Les pirates informatiques peuvent utiliser ces jetons pour différentes raisons, notamment accéder à une API privée qui ne leur est pas accessible (certains accès API peuvent être liés à un compte et ainsi accéder à des données privées. Cela peut être le cas par exemple avec l'API Spotify qui permet d'accéder à vos données privées via votre clé API), voler des crédits payants, abuser de l'accès jusqu'à ce que la clé soit bannie pour trop de requêtes par exemple.

Au lieu d'écrire les jetons à l'intérieur du code comme une variable, il est préférable de les écrire dans un fichier \texttt{config.properties} et d'ajouter ce fichier au \texttt{.gitignore}.

Pour les projets professionnels, des outils spécialisés comme Azure Key Vault peuvent être utilisés.

D'autres outils peuvent permettre aux développeurs de scanner les modifications avant de commiter automatiquement, ou de scanner un dépôt pour vérifier si des secrets sont inclus dans le code.

\subsection{Choix du nombre de partitions}

Le dimensionnement des partitions pour chaque topic est justifié par les conditions réelles d'exploitation et les volumes de données attendus :

\subsubsection{Topic \texttt{raw-tweets} : 1 partition}

\textbf{Justification :} Dans un contexte de production réel avec un volume important de tweets (millions par jour), ce topic nécessiterait plusieurs partitions pour paralléliser l'ingestion. Cependant, pour ce TP avec un dataset limité et un besoin de préserver l'ordre chronologique des tweets lors de leur lecture, une seule partition suffit et simplifie l'implémentation.

\subsubsection{Topic \texttt{filtered-tweets} : 1 partition}

\textbf{Justification :} Le filtrage réduit considérablement le volume de données. Même en production avec de gros volumes initiaux, le débit après filtrage restrait gérable par une seule partition pour un grand nombre de données(ou en tout cas, beaucoup moins qu'inititalement). 

\subsubsection{Topic \texttt{hashtags} : 3 partitions}

\textbf{Justification :} C'est le topic critique nécessitant du partitionnement :
\begin{itemize}
    \item \textbf{Volume élevé :} Chaque tweet peut contenir plusieurs hashtags, multipliant le nombre de messages
    \item \textbf{Cohérence du comptage :} Le partitionnement par clé (hashtag) garantit que tous les messages concernant un même hashtag arrivent à la même partition, permettant un comptage cohérent
    \item \textbf{Parallélisation :} 3 partitions permettent de distribuer la charge sur 3 instances de \texttt{KafkaHashtagCounter} via un consumer group
\end{itemize}

Le nombre de 3 est indicatif comme les autres, basé sur le fait qu'on s'attend à avoir environ 3 hashtags par tweet en moyenne. Pour le TP, une seule partitiuon suffit. 

\subsubsection{Topic \texttt{leaderboard} : 1 partition}

\textbf{Justification :} Ce topic contient uniquement les agrégations finales (top N hashtags), donc un très faible volume de messages. Une seule partition suffit et permet de préserver l'ordre temporel des mises à jour du classement pour l'affichage.

\section{Analyse des risques / Analyse initiale des risques}

\underline{Impact d'une défaillance du Tweet Producer} :

Les nouveaux tweets ne sont plus reçus par l'application.

Il n'y aura pas de crash, et la restauration de cet élément permettra à l'application de fonctionner à nouveau normalement.

\underline{Impact d'une défaillance du Tweet Filter} :

Les tweets bruts ne sont pas filtrés et transmis aux composants suivants. Les messages s'accumuleront dans le topic \texttt{raw-tweets}. La restauration de cet élément entraînera le filtrage de tous les tweets bruts sans aucune perte d'information.

\underline{Impact d'une défaillance du Hashtag Extractor} :

Les hashtags ne sont plus extraits des tweets. Les tweets filtrés s'accumuleront dans le topic \texttt{filtered-tweets}. La restauration de cet élément entraînera l'extraction des hashtags des tweets filtrés sans aucune perte d'information.

\underline{Impact d'une défaillance du Hashtag Counter} :

Les hashtags ne sont plus comptabilisés. Sans mesure supplémentaire, la restauration de cet élément peut entraîner des erreurs dans les résultats : la mémoire du nombre d'apparitions passées de chaque hashtag sera perdue et réinitialisée à $0$.

\underline{Impact d'une défaillance du Visualizor} :

Il n'est plus possible de voir les résultats. La restauration de cet élément permettra d'afficher à nouveau les résultats, sans aucune erreur dans les données affichées.

\underline{Impact d'une défaillance d'un Broker} :

La défaillance d'un broker ne sera pas un problème s'il est répliqué.



\section{Task 9}

\subsection{Compilation}

Tous les composants Kafka ont été implémentés en Java et compilés avec Maven. La compilation s'effectue avec la commande suivante :

mvn -f ./pom.xml clean package

Note importante : La structure du pom.xml a dû être modifiée pour être correcte pour éviter des erreurs de compilation et des dépendances manquantes. C'est cette commande qui crée tous les .jar qui seront exécutés dans le terminal pour lancer les services Kafka. 

Les fichiers .jar sont créés sous :

target/<Nom du service>-jar-with-dependencies.jar

Par exemple, pour le producer des raw-tweets:

java -jar target/KafkaTweetProducer-jar-with-dependencies.jar

\subsection{Serveur Kafka}

Avant de lancer les composants, le serveur Kafka doit être démarré :

\textbf{Génération d'un UUID pour le cluster :}

\begin{verbatim}
KAFKA_CLUSTER_ID="$($KAFKA_HOME/bin/kafka-storage.sh random-uuid)"
\end{verbatim}

\textbf{Formatage du storage :}

\begin{verbatim}
$KAFKA_HOME/bin/kafka-storage.sh format --standalone -t $KAFKA_CLUSTER_ID \
  -c $KAFKA_HOME/config/server.properties
\end{verbatim}

\textbf{Démarrage du serveur Kafka :}

\begin{verbatim}
$KAFKA_HOME/bin/kafka-server-start.sh $KAFKA_HOME/config/server.properties
\end{verbatim}

\subsection{Création des topics}

Les topics nécessaires doivent être créés avant le lancement des composants :

\textbf{Topic pour les tweets bruts :}

\begin{verbatim}
$KAFKA_HOME/bin/kafka-topics.sh --create --bootstrap-server localhost:9092 \
  --replication-factor 1 --partitions 1 --topic raw-tweets
\end{verbatim}

\textbf{Topic pour les tweets filtrés :}

\begin{verbatim}
$KAFKA_HOME/bin/kafka-topics.sh --create --bootstrap-server localhost:9092 \
  --replication-factor 1 --partitions 1 --topic filtered-tweets
\end{verbatim}

\textbf{Topic pour les hashtags extraits :}

\begin{verbatim}
$KAFKA_HOME/bin/kafka-topics.sh --create --bootstrap-server localhost:9092 \
  --replication-factor 1 --partitions 1 --topic hashtags
\end{verbatim}

\textbf{Topic pour le leaderboard :}

\begin{verbatim}
$KAFKA_HOME/bin/kafka-topics.sh --create --bootstrap-server localhost:9092 \
  --replication-factor 1 --partitions 1 --topic leaderboard
\end{verbatim}


\subsection{Lancement des composants}

\textbf{KafkaTweetProducer}

Commande:

java -jar target/KafkaTweetProducer-jar-with-dependencies.jar [random|recorded]

Options:

\begin{enumerate}
\item random: implémente le producer random présent dans la version initiale du projet. 

\item recorded: implémente le producer lisant un fichier contenant des tweets au format .json.

Pour l'utiliser, il faut bien penser à créer une variable d'environnement précisant où se trouve le fichier source:

export tweetoscope\_sourcefile="..."

Contrairement au random, il ne fonctionne pas indéfiniment. Il ne lit qu'une seule fois le contenu du fichier puis s'arrête. 
 
\end{enumerate}

\textbf{KafkaTweetFilter}

Ce composant consomme les tweets du topic raw-tweets, les filtre et publie les tweets filtrés dans filtered-tweets :

java -jar target/KafkaTweetFilter-jar-with-dependencies.jar [option] [paramètre]

Note d'implémentation : La classe RecentTweetFilter a été réimplémentée sans utiliser le pattern .subscribe(). Cette approche diffère du code initial mais respecte le modèle consumer-producer de Kafka.

Options:

\begin{enumerate}
\item recent 

Comportement : Ne conserve que les tweets créés il y a moins de 24 heures.

Critère : Compare la date de création du tweet (createdAt) avec l'heure actuelle.

\item lang [codelangue] 

Comportement : Ne conserve que les tweets dans la langue spécifiée. Si aucun code de langue n'est fourni, "en" (anglais) est utilisé par défaut.

Critère : Compare le champ lang du tweet avec le code langue fourni.

\item empty

Comportement : Ne filtre que les tweets ayant un contenu textuel non vide (après suppression des espaces).

\end{enumerate}

\textbf{KafkaHashtagExtractor}

Ce composant consomme les tweets filtrés et extrait les hashtags :

java -jar target/KafkaHashtagsExtractor-jar-with-dependencies.jar

\textbf{KafkaHashtagCounter}

Ce composant compte les occurrences de chaque hashtag et publie les résultats dans le topic leaderboard :
java -jar target/KafkaHashtagCounter-jar-with-dependencies.jar

\textbf{Leaderboard}

Ce composant consomme le topic leaderboard et affiche les résultats :

java -jar target/KafkaLeaderboard-jar-with-dependencies.jar

\section{Vérification expérimentale de l'analyse des risques}

\subsection{Défaillance du Tweet Producer}

Gravité: Moyenne à forte

$\rightarrow$ Le leaderboard reste affiché avec des informations qui deviennent de plus en plus fausses pendant la durée de la panne. Le problème est que remettre le producer en route (en supposant qu'on est Online, connectés à l'API) ne nous permet pas de récupérer les Tweets publiés entre temps. Les informations affichées seront donc faussées durant une certaine période, qui peut dépendre par exemple du temps mis dans le filtre "recent" s'il est utilisé. 

Détectabilité: Moyenne ou forte

$\rightarrow$ Il n'y a pas de message d'erreur, mais on remarquera assez facilement que le leaderboard ne se met plus à jour

\subsection{Défaillance du Tweet Filter}

Gravité: Faible

$\rightarrow$ Les tweets bruts s'accumulent dans le topic \texttt{raw-tweets} sans être traités. Le reste de la chaîne continue de fonctionner normalement avec les derniers tweets filtrés. Aucun composant ne crashe. Lorsque le filtre est relancé, il reprend le traitement de tous les tweets accumulés grâce au mécanisme de consumer groups de Kafka, sans perte de données.

Détectabilité: Moyenne

$\rightarrow$ Aucun message d'erreur visible. On peut détecter la panne en vérifiant le lag du consumer group qui augmente progressivement, ou en constatant que de nouveaux tweets ne sont plus filtrés alors que le producer continue de publier.

\subsection{Défaillance du Hashtag Extractor}

Gravité: Faible

$\rightarrow$ Les tweets filtrés s'accumulent dans le topic \texttt{filtered-tweets} sans que les hashtags soient extraits. Le comportement est similaire à la défaillance du filtre : le système reste stable, les messages s'accumulent, et la reprise du service permet de traiter l'intégralité des tweets en attente sans perte de données.

Détectabilité: Moyenne

$\rightarrow$ Pas de message d'erreur. La détection se fait par l'observation du lag du consumer group correspondant, ou par l'absence de mise à jour du leaderboard alors que de nouveaux tweets filtrés arrivent.

\subsection{Défaillance du Hashtag Counter}

Gravité: Forte

$\rightarrow$ Les hashtags extraits s'accumulent dans le topic \texttt{hashtags} mais ne sont plus comptabilisés. Le problème majeur confirmé expérimentalement est la \textbf{perte de l'état en mémoire} : lorsque le counter est relancé, les compteurs repartent à zéro. Les hashtags reçus pendant la panne sont bien traités à la reprise, mais l'historique des comptages précédents est perdu, ce qui fausse complètement les résultats du leaderboard.

Détectabilité: Forte

$\rightarrow$ La détection est immédiate après redémarrage : on observe que les compteurs ont été réinitialisés (ex: un hashtag qui était à 50 apparitions repasse à 0 ou à un petit nombre). Cette anomalie dans les valeurs affichées permet de détecter rapidement qu'il y a eu une défaillance.

\subsection{Défaillance du Visualiseur}

Gravité: Très faible

$\rightarrow$ L'affichage du leaderboard n'est plus disponible, mais toute la chaîne de traitement continue de fonctionner normalement. Les résultats continuent d'être produits et publiés dans le topic \texttt{leaderboard}. Lorsque le visualiseur est relancé, il affiche immédiatement les dernières données disponibles sans aucune perte d'information.

Détectabilité: Immédiate

$\rightarrow$ L'absence d'affichage est immédiatement visible pour l'utilisateur. Cependant, on peut vérifier que les données continuent d'être produites en consultant directement le topic \texttt{leaderboard} avec un consumer console.

\subsection{Défaillance d'un Broker}

Gravité: Critique (sans réplication) / Faible (avec réplication)

$\rightarrow$ Dans notre configuration actuelle avec un seul broker (\texttt{replication-factor=1}), la défaillance du broker entraîne l'arrêt complet de l'application : tous les topics deviennent inaccessibles et tous les composants sont bloqués. Avec une configuration répliquée sur plusieurs brokers, la défaillance d'un broker n'affecterait pas le fonctionnement global grâce à la redistribution automatique des partitions sur les brokers restants.

Détectabilité: Immédiate

$\rightarrow$ Tous les composants génèrent des erreurs de connexion et l'application s'arrête complètement. La détection est donc immédiate.

\section{Task 11 : Conteneurisation Docker}

\subsection{Avantages de la Conteneurisation avec Docker}

Docker révolutionne le déploiement d'applications en résolvant le problème ``ça marche sur ma machine''. Voici les avantages clés :

\begin{itemize}
    \item \textbf{Exécutabilité universelle} : Une fois packagée en image Docker, l'application fonctionne \textbf{partout} — sur un laptop en développement, un serveur de test, ou en production — sans modification du code
    
    \item \textbf{Dépendances complètes} : L'image contient l'intégralité de l'environnement (OS minimal, JRE, librairies) pour exécuter l'application. Aucune installation préalable requise
    
    \item \textbf{Isolation garantie} : Chaque conteneur a son propre système de fichiers, variables d'environnement et processus isolés des autres. Pas de conflits de dépendances
    
    \item \textbf{Rapidité de déploiement} : Lancer un conteneur prend quelques secondes, contrairement aux machines virtuelles qui demandent plusieurs minutes
    
    \item \textbf{Scalabilité instantanée} : Créer 5 copies identiques d'un service n'est qu'une commande Docker Compose
    
    \item \textbf{Reproductibilité} : Les versions exactes de tous les outils (Maven, JRE, Kafka) sont figées. Aucun risque de ``version différente qui casse tout''
    
    \item \textbf{Portabilité entre environnements} : Le même conteneur s'exécute sur macOS, Linux, Windows, ou cloud (AWS, Azure, Google Cloud)
\end{itemize}

\subsection{Architecture Multi-Stage du Dockerfile}

Nous avons créé un Dockerfile avec une \textbf{architecture multi-stage} pour optimiser l'image finale. Cette approche utilise deux étapes distinctes :

\subsubsection{Stage 1 : Compilation (Build)}

Cette première étape utilise l'image \texttt{maven:3.9-eclipse-temurin-11} contenant Maven et le compilateur Java. Ses rôles :

\begin{itemize}
    \item Cloner/copier le code source du projet Tweetoscope
    \item Compiler le code Java avec Maven
    \item Générer les fichiers \texttt{.jar} de tous les microservices (KafkaTweetProducer, KafkaTweetFilter, KafkaHashtagExtractor, KafkaHashtagCounter, KafkaLeaderboard)
    \item Créer les JARs ``fat-jar'' (avec toutes les dépendances incluses) dans \texttt{target/}
\end{itemize}

\subsubsection{Stage 2 : Runtime (Exécution)}

La deuxième étape utilise l'image légère \texttt{eclipse-temurin:11-jre-alpine} (~150 MB) contenant uniquement la JRE, \textbf{sans les outils de compilation}. Ses rôles :

\begin{itemize}
    \item Copier les fichiers \texttt{.jar} générés au stage 1
    \item Configurer les variables d'environnement pour spécifier le service à lancer
    \item Exposer le port 8080 pour le leaderboard web server
    \item Lancer le service approprié selon les variables d'environnement passées
\end{itemize}

\subsubsection{Avantage de cette approche}

\textbf{Réduction de taille} : En éliminant Maven et le compilateur de l'image finale, on obtient une image de \textbf{~200 MB} au lieu de \textbf{800+ MB}. Cela accélère le pull, le déploiement et économise l'espace disque.

\subsubsection{Construction de l'Image}

Pour construire l'image Docker localement (depuis le répertoire contenant le Dockerfile) :

\begin{verbatim}
docker build -t fthievon/tweetoscope-kafka:latest .
\end{verbatim}

\textbf{Résultat :} Une image \texttt{tweetoscope-kafka:latest} prête à être utilisée, contenant tous les services Kafka packagés.

\subsubsection{Variables d'environnement}

L'image est paramétrée via trois variables d'environnement permettant de spécifier quel service lancer et comment :

\begin{itemize}
    \item \texttt{SERVICE\_JAR} : Le nom du JAR à exécuter (ex: \texttt{KafkaTweetFilter}, \texttt{KafkaHashtagCounter})
    \item \texttt{KAFKA\_BOOTSTRAP\_SERVERS} : L'adresse du broker Kafka (ex: \texttt{kafka:9092} pour Docker Compose)
    \item \texttt{ARGS} : Arguments supplémentaires (ex: \texttt{lang en} pour le filtre de langue)
\end{itemize}

\subsection{Publication sur DockerHub}

Après construction locale, l'image est poussée sur le registre public DockerHub pour la rendre accessible à tous :

\subsubsection{Commande de Push}

\begin{verbatim}
docker push fthievon/tweetoscope-kafka:latest
\end{verbatim}

\textbf{Résultat :} L'image est maintenant disponible publiquement sur DockerHub à l'adresse \texttt{https://hub.docker.com/r/fthievon/tweetoscope-kafka}.

\subsection{Orchestration avec Docker Compose}

Docker Compose permet de \textbf{décrire et lancer} tout l'écosystème Tweetoscope en une seule commande. Le fichier \texttt{docker-compose.yml} définit tous les conteneurs et leurs relations.

\subsubsection{Architecture Complète - 7 Conteneurs en Cascade}

Notre \texttt{docker-compose.yml} orchestre \textbf{7 conteneurs} lancés en cascade :

\textbf{Phase 1 : Infrastructure Kafka}

\begin{enumerate}
    \item \textbf{Conteneur Kafka} (image : \texttt{apache/kafka:latest})
    \begin{itemize}
        \item \textbf{Nom} : \texttt{kafka}
        \item \textbf{Rôle} : Message broker central stockant les 4 topics (raw-tweets, filtered-tweets, hashtags, leaderboards)
        \item \textbf{Mode} : KRaft (pas de Zookeeper nécessaire, architecture simplifiée)
        \item \textbf{Port exposé} : 9092 (Bootstrap server pour la communication intra-cluster)
        \item \textbf{Vérification santé} : Healthcheck à 6.5 secondes
        \item \textbf{Topics créés automatiquement} : raw-tweets, filtered-tweets, hashtags, leaderboards
    \end{itemize}

    \item \textbf{Conteneur Topic Creator} (image : \texttt{edenhill/kcat:latest})
    \begin{itemize}
        \item \textbf{Nom} : \texttt{topic-creator}
        \item \textbf{Rôle} : Crée les 4 topics Kafka nécessaires, puis s'arrête (lifecycle temporaire)
        \item \textbf{Dépendance} : Attend que Kafka soit \texttt{healthy} (6.5s)
        \item \textbf{Topics créés} :
        \begin{itemize}
            \item \texttt{raw-tweets} : 3 partitions (input du producer)
            \item \texttt{filtered-tweets} : 3 partitions (output du filter)
            \item \texttt{hashtags} : 3 partitions (output de l'extractor)
            \item \texttt{leaderboards} : 1 partition (output du counter)
        \end{itemize}
        \item \textbf{Durée} : ~24 secondes, puis \texttt{Exited}
    \end{itemize}
\end{enumerate}

\textbf{Phase 2 : Microservices Tweetoscope (basés sur notre image \texttt{fthievon/tweetoscope-kafka:latest})}

\begin{enumerate}
    \setcounter{enumi}{2}
    \item \textbf{Conteneur tweetoscope-producer} (image : \texttt{fthievon/tweetoscope-kafka:latest})
    \begin{itemize}
        \item \textbf{Rôle} : Produit ~55k tweets aléatoires dans le topic \texttt{raw-tweets}
        \item \textbf{Commande} : \texttt{java -cp /app/jars/* tweetoscope.kafka.KafkaTweetProducer}

\section{Tâche 12 : Déploiement Kubernetes}

\subsection{Présentation du déploiement}

L’application Tweetoscope, précédemment conteneurisée avec Docker (Tâche 11), a été déployée sur un cluster Kubernetes afin de tirer parti des capacités d’orchestration et d’améliorer la tolérance aux pannes. L’architecture de déploiement est composée de plusieurs microservices communiquant via des topics Apache Kafka.

Le cluster a été configuré en mode multi-nœuds à l’aide de Kind (Kubernetes in Docker), comprenant un nœud \textit{control-plane} et deux nœuds \textit{worker}. Cette configuration permet la répartition des pods entre plusieurs nœuds, constituant ainsi la base des tests de tolérance aux pannes.

\subsection{Ressources Kubernetes utilisées}

Le déploiement exploite plusieurs types de ressources Kubernetes pour orchestrer les microservices de Tweetoscope.

\subsubsection{Deployments}

Chaque microservice (Producer, Filter, Extractor, Counter, Leaderboard) est géré par un objet \texttt{Deployment}, qui garantit qu’un nombre souhaité de réplicas de pods est toujours en cours d’exécution. Actuellement, chaque Deployment est configuré avec un seul replica (\texttt{replicas: 1}), bien qu’un passage à l’échelle horizontal soit possible pour améliorer la disponibilité. Le broker Kafka est également déployé sous forme de Deployment, avec une politique de redémarrage \texttt{Always}, permettant une reprise automatique en cas de crash.

\subsubsection{Services}

Deux Services de type \texttt{ClusterIP} sont déployés :

\begin{itemize}
    \item \texttt{kafka} : expose le broker Kafka en interne sur le port 9092, offrant une résolution DNS stable (\texttt{kafka:9092}) à tous les pods producteurs et consommateurs. Cette abstraction découple les pods des adresses IP dynamiques attribuées aux pods Kafka.
    \item \texttt{tweetoscope-leaderboard} : expose l’API Leaderboard sur le port 8080, permettant l’accès à l’endpoint de classement en temps réel.
\end{itemize}

\subsection{PersistentVolumeClaim : Implémentation et contraintes}

Le Deployment Kafka était initialement conçu pour utiliser un \textbf{PersistentVolumeClaim (PVC)} afin d’assurer la persistance des données. Un PVC est une ressource Kubernetes qui demande du stockage au cluster, en abstrahant l’infrastructure sous-jacente (NFS, volumes cloud, disques locaux, etc.). Cette configuration a été testée avec succès dans un cluster local multi-nœuds utilisant Kind.

L’utilisation d’un PVC fournirait :

\begin{itemize}
    \item \textbf{Durabilité des données à travers le cycle de vie du pod} : les données persistent malgré les redémarrages, crashs ou reschedulings.
    \item \textbf{Persistance au-delà du Deployment} : les données restent, même si le Deployment est supprimé puis recréé.
    \item \textbf{Résilience face aux pannes de nœud} : le stockage est découplé du nœud hébergeant.
    \item \textbf{Séparation des responsabilités} : calcul (pods) et stockage (volumes) gérés indépendamment.
\end{itemize}

\subsubsection*{Contrainte de déploiement : Permissions du cluster}

Cependant, lors du déploiement sur le cluster Kubernetes de l’école, le PVC restait dans l’état \texttt{Pending} avec l’erreur suivante :

\begin{quote}
\textit{``no persistent volumes available for this claim and no storage class is set''}
\end{quote}

\subsubsection{Cause racine}

Le problème vient du fait que le cluster ne fournit pas de \texttt{StorageClass} par défaut pour la provision dynamique, ni de \texttt{PersistentVolumes} préalloués accessibles aux namespaces étudiants. De plus, les privilèges administrateurs nécessaires pour configurer des ressources de stockage ne sont pas disponibles.

\subsubsection{Tests effectués}

La fonctionnalité PVC a été vérifiée avec succès sur des clusters locaux Kubernetes utilisant Kind. Toutefois, sur le cluster de l’école, les PVC ne peuvent pas être utilisés en raison de restrictions de permissions liées au stockage.

\subsubsection{Solution de production : \texttt{emptyDir}}

Pour le déploiement sur le cluster de l’école, l’implémentation utilise à la place un volume \texttt{emptyDir}.

\subsubsection{Caractéristiques d’emptyDir}

Un volume \texttt{emptyDir} fournit un stockage éphémère sur le nœud hébergeant le pod Kafka et persiste uniquement tant que le pod continue de s’exécuter sur ce même nœud. Il supporte également les redémarrages du pod gérés par le contrôleur de Deployment.

Cependant, les données sont perdues lorsque :

\begin{itemize}
    \item le pod est reschedulé sur un autre nœud,
    \item le Deployment est supprimé,
    \item le nœud tombe en panne.
\end{itemize}

\subsubsection{Job de création des topics}

Un Job Kubernetes (\texttt{topic-creator}) est exécuté une seule fois lors du déploiement pour créer les topics Kafka nécessaires (\texttt{raw-tweets}, \texttt{filtered-tweets}, \texttt{hashtags}, \texttt{leaderboards}). Le Job s’exécute jusqu’à sa complétion et ne redémarre pas, garantissant une initialisation idempotente des topics.

\section{Atténuation des risques grâce à Kubernetes}

\subsection{Lien avec l’analyse de risques initiale}

Dans la Tâche 8, nous avions identifié plusieurs risques critiques inhérents à l’architecture Tweetoscope :

\begin{enumerate}
    \item \textbf{Crash de composants} : panne d’un producteur, consommateur ou broker Kafka entraînant une interruption de service.
    \item \textbf{Panne de nœud} : panne matérielle ou réseau rendant indisponibles tous les pods d’un nœud.
    \item \textbf{Perte de données} : perte de messages en transit ou de données Kafka persistantes suite à une panne de stockage.
    \item \textbf{Epuisement des ressources} : fuites mémoire ou pics CPU provoquant des crashs et des pannes en cascade.
    \item \textbf{Erreurs de déploiement} : mises à jour défectueuses entraînant une indisponibilité.
\end{enumerate}

Kubernetes n’élimine pas complètement ces risques mais fournit des mécanismes robustes pour détecter les pannes, automatiser la reprise et réduire les temps d’indisponibilité. Les sous-sections suivantes analysent la manière dont Kubernetes atténue chaque scénario comparé à Docker seul ou à une orchestration manuelle.

\subsection{Scénarios de panne et atténuations}

\subsubsection{Scénario 1 : Crash de pod (ex. Producer ou Consumer)}

\textbf{Sans Kubernetes} : si un producteur crash à cause d’une exception non gérée ou d’une fuite mémoire, le service s’arrête indéfiniment jusqu’à intervention manuelle. Aucun tweet n’est généré durant cette période, créant un trou dans le pipeline.

\textbf{Avec Kubernetes} : le Deployment surveille en continu l’état désiré (\texttt{replicas: 1}). Lorsqu’un pod crash, Kubernetes programme automatiquement un nouveau pod, généralement en 20--40 secondes. Le nouveau pod se reconnecte à Kafka via le nom DNS stable \texttt{kafka:9092} et reprend son traitement.

\textbf{Impact} : léger retard temporaire, mais aucune perte définitive grâce à Kafka.

\subsubsection{Scénario 2 : Panne d’un nœud worker}

\textbf{Sans Kubernetes} : les services deviennent indisponibles et doivent être redémarrés manuellement sur une autre machine.

\textbf{Avec Kubernetes (PVC local)} : le control-plane détecte la panne et reschedule les pods. Les services stateless récupèrent instantanément. Kafka récupère ses données persistées.

\textbf{Avec Kubernetes sur le cluster école (emptyDir)} : Kafka est reschedulé mais perd son état car le stockage est local.

\textbf{Impact} :  
1 ou 2 minutes d’indisponibilité pour les services stateless, 2 ou 3 minutes pour Kafka.  
Possibilité de perte de données avec \texttt{emptyDir}.

\subsubsection{Scénario 3 : Crash du broker Kafka}

\textbf{Sans Kubernetes} : arrêt du pipeline, redémarrage manuel requis.

\textbf{Avec Kubernetes (PVC)} : redémarrage automatique, récupération des logs.

\textbf{Avec Kubernetes (emptyDir)} : les données persistent uniquement si le pod redémarre sur le même nœud.

\textbf{Impact} : courte indisponibilité avec PVC, pertes possibles avec \texttt{emptyDir}.

\subsubsection{Scénario 4 : Échec de mise à jour continue}

\textbf{Sans Kubernetes} : downtime et rollback manuel.

\textbf{Avec Kubernetes} : rolling updates sans interruption. Les checks de santé stoppent les déploiements défectueux.

\textbf{Impact} : mises à jour sans arrêt pour les microservices stateless.

\subsubsection{Scénario 5 : Epuisement des ressources (fuite mémoire)}

\textbf{Sans Kubernetes} : peut impacter l’ensemble de la machine.

\textbf{Avec Kubernetes} : les limites de ressources tuent et redémarrent automatiquement les pods, empêchant les effets en cascade.

\textbf{Impact} : perturbation mineure, stabilité globale maintenue.

\subsection{Limites de l’atténuation Kubernetes}

Bien que Kubernetes améliore significativement la tolérance aux pannes, il ne constitue pas une solution miracle :

\begin{itemize}
    \item \textbf{Risques de perte de données} : Kubernetes ne peut compenser une configuration Kafka incorrecte (ex. \texttt{acks=0}). Avec un broker unique, une panne disque entraînant une perte définitive est possible.
    \item \textbf{Duplication de messages} : pendant un redémarrage, un consommateur Kafka peut retraiter des messages si les offsets ne sont pas commit de manière transactionnelle.
    \item \textbf{Erreurs de configuration} : Kubernetes ne détecte pas les erreurs logiques (mauvais topics, mauvaise sérialisation).
    \item \textbf{Points uniques de défaillance} : un seul broker Kafka et des microservices avec un seul replica créent des fentes lors des redémarrages. Une réplication (\texttt{replicas: 3}) et un cluster Kafka multi-brokers résoudraient cela.\\[0.3em]
    \textit{Note : lors des tests locaux, passer à plusieurs replicas ou plusieurs brokers Kafka surchargeait Docker, causant des crashs du daemon par saturation CPU/mémoire. Malgré cela, les scénarios de panne de nœud avec PVC ont été validés avec persistance intacte.}
    \item \textbf{Panne du control-plane} : sans un control-plane hautement disponible, aucun nouveau pod ne peut être programmé.
\end{itemize}

En conclusion, Kubernetes transforme l’architecture Tweetoscope d’un système fragile et géré manuellement en une plateforme auto-réparatrice et scalable. Toutefois, une véritable haute disponibilité nécessite des stratégies complémentaires : réplication Kafka, multiples replicas, probes de santé, limites de ressources et supervision avancée.

\section{Task 16 : Intégrer un process pour check la qualité du code avec SonarQube dans la pipeline CI/CD GitLab}


\textbf{Objectif :} Analyser la qualité du code source avec SonarQube Community Edition.

\textbf{Configuration :}

\begin{itemize}
    \item \textbf{Image Docker} : \texttt{maven:3.9-eclipse-temurin-11}
    \item \textbf{Service Docker} : \texttt{sonarqube:10.3-community} (lancé en conteneur)
    \item \textbf{Commande} : \texttt{mvn clean verify sonar:sonar} avec paramètres SonarQube
\end{itemize}

\textbf{Processus d'exécution :}

\begin{enumerate}
    \item \textbf{Attente du démarrage de SonarQube} : Boucle de 120 tentatives avec vérification de santé via HTTP
    \item \textbf{Pause d'initialisation} : 30 secondes supplémentaires pour la stabilisation complète
    \item \textbf{Compilation et test} : \texttt{mvn clean verify} compile le projet et exécute les tests
    \item \textbf{Analyse SonarQube} : \texttt{sonar:sonar} lance le scanner et envoie les résultats à SonarQube
\end{enumerate}

\subsubsection{Métriques Analysées par SonarQube}

SonarQube analyse les aspects suivants :

\begin{itemize}
    \item \textbf{Bugs} : Défauts logiques et erreurs de programmation
    \item \textbf{Vulnerabilities} : Failles de sécurité potentielles
    \item \textbf{Code Smells} : Mauvaises pratiques et code peu maintenable
    \item \textbf{Duplications} : Code dupliqué inutilement
    \item \textbf{Complexité} : Complexité cyclomatique des méthodes
    \item \textbf{Maintenabilité} : Notation globale de la qualité (A-E)
\end{itemize}

\textbf{Résultats observés dans cette exécution :}

\begin{itemize}
    \item 27 fichiers source indexés (26 fichiers principaux + 1 fichier test)
    \item 100\% des fichiers analysés avec succès
    \item CPD (Copy-Paste Detector) : 6 fichiers sans blocs copiés, 20 fichiers analysés pour duplication
    \item Rapport d'analyse généré : 358.9 kB, compressé à 125.7 kB
\end{itemize}

\subsubsection{Visualiser les Résultats SonarQube}

Après l'exécution du job, le message suivant apparaît dans les logs :

\begin{verbatim}
[INFO] ANALYSIS SUCCESSFUL, you can find the results at:
http://sonarqube:9000/dashboard?id=tweetoscope
\end{verbatim}

\textbf{Limitations :} SonarQube s'exécute en conteneur temporaire, donc les données ne sont pas persistées après le job. Les logs du job contiennent les détails complets de l'analyse.

\textbf{Pour voir les résultats détaillés :}

\begin{enumerate}
    \item Accédez à \textbf{CI/CD} → \textbf{Pipelines} dans GitLab
    \item Cliquez sur le pipeline correspondant
    \item Sélectionnez le job \textbf{sonarqube-scan}
    \item Consultez les \textbf{Logs} pour voir les détails de l'analyse
    \item Cherchez la section ``ANALYSIS SUCCESSFUL'' pour les métriques
\end{enumerate}

\section{Conclusion}

La réalisation de ce projet nous a permis d’explorer de manière concrète un ensemble de technologies modernes utilisées dans les architectures distribuées. Nous avons appris à concevoir une pipeline orientée événements avec Kafka, à conteneuriser des services, à orchestrer leur déploiement via Kubernetes et à mettre en place un pipeline CI/CD complet sur GitLab. Plus globalement, nous avons développé une compréhension approfondie des problématiques de tolérance aux pannes, de scalabilité, de découplage entre composants et de livraison continue.

La partie la plus difficile du projet a été la transition depuis l’application Java monolithique vers une architecture distribuée reposant sur Kafka. Il a fallu repenser complètement les interactions entre les éléments du pipeline, définir des schémas de messages, gérer les offsets et comprendre les comportements réels d’un système asynchrone. Le déploiement sur Kubernetes a également représenté un défi : la configuration des services, la gestion des pods et l’observation du comportement du système face aux pannes nécessitent un certain temps d’apprentissage et beaucoup d’expérimentations.

Concernant l’usage d’outils d’IA, nous en avons effectivement utilisé plusieurs, principalement ChatGPT et GitHub Copilot. Nous les avons sollicités pour différentes catégories de tâches : aide à la rédaction du rapport (clarification de sections, reformulation), assistance pour comprendre certains concepts (fonctionnement des partitions Kafka, configuration des consumers), génération de squelettes de fichiers YAML ou Dockerfile, et aide ponctuelle pour corriger des erreurs de configuration ou de code.
Ces outils se sont révélés précieux, mais pas toujours directement applicables. L’IA nous a permis de gagner du temps sur des tâches que nous savions réaliser mais qui demandaient beaucoup de recherches (par exemple la syntaxe précise des manifests Kubernetes). Elle nous a aussi appris certains aspects techniques que nous maîtrisions peu, notamment sur les subtilités du comportement des consumers Kafka ou sur les bonnes pratiques de CI/CD.
Obtenir une réponse exploitable demandait parfois plusieurs itérations, notamment pour les fichiers de configuration complexes. Quelques tentatives ont été abandonnées lorsque les propositions n’étaient pas adaptées à notre contexte précis, ce qui nous a obligés à revenir à la documentation officielle, confirmant que l’IA doit être utilisée comme un outil d’aide, mais jamais comme une source unique de vérité.

En définitive, ce projet nous a apporté une expérience complète, mêlant conception logicielle, technologies cloud-native, automatisation et documentation. L’usage d’outils d’IA a été un support utile, mais la compréhension du système et la résolution des problèmes ont reposé avant tout sur notre propre travail d’analyse, d’expérimentation et d’intégration.
